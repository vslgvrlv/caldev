# Тестовые сценарии PBTH: наполнитель и что в нём

Наполнитель создаёт команды, людей и события, на которых один настоящий
аккаунт («главный человек») проходит большую часть действий приложения в
разных ролях. Код: `backend/src/db/seeds/scenarios.ts` (запуск, защита,
вывод), `backend/src/db/seeds/scenarios/plan.ts` (сами данные),
`apply.ts` (запись и удаление), `guard.ts` (защита от прода), `ids.ts` (метки).
Тесты: `backend/src/__tests__/unit/seed-scenarios-guard.test.ts`,
`backend/src/__tests__/integration/seed-scenarios.test.ts`.

## Запуск

Главный человек уже должен существовать: наполнитель его не создаёт, а
находит по telegram id (или по id пользователя) и добавляет в тестовые
команды. Его настоящие команды, события, ответы и роли не меняются.

Локальный стенд (база на этом компьютере):

```
cd backend
SEED_SCENARIOS_ALLOW=local DB_PORT=<порт> FRONTEND_URL=http://127.0.0.1:<порт фронта> \
  npm run db:seed:scenarios -- --owner-telegram-id 9000000101 --dry-run
SEED_SCENARIOS_ALLOW=local ... npm run db:seed:scenarios -- --owner-telegram-id 9000000101
```

На стенде владелец платформы задаётся `ADMIN_ROLE_ALLOWLIST_IDS` у бэкенда;
войти под главным человеком — `GET /api/v1/auth/dev/login?telegramId=<id>&ensureTeam=0&redirectTo=/app`.
Без `ensureTeam=0` вход через dev-ссылку заводит человеку без команды новую
команду «Local Dev Team».

Staging (внутри контейнера бэкенда, после выката релиза с этим скриптом):

```
docker exec -e SEED_SCENARIOS_ALLOW=staging pbth-staging-backend-1 \
  node dist/db/seeds/scenarios.js --owner-telegram-id <telegram id владельца> --dry-run
docker exec -e SEED_SCENARIOS_ALLOW=staging pbth-staging-backend-1 \
  node dist/db/seeds/scenarios.js --owner-telegram-id <telegram id владельца>
```

`DB_NAME`, `DB_HOST`, `FRONTEND_URL` контейнер берёт из `staging.env`. Telegram
id владельца — тот, что стоит в `ADMIN_ROLE_ALLOWLIST_IDS` этого же файла.

Удалить всё тестовое и только его:

```
docker exec -e SEED_SCENARIOS_ALLOW=staging pbth-staging-backend-1 node dist/db/seeds/scenarios.js --remove --dry-run
docker exec -e SEED_SCENARIOS_ALLOW=staging pbth-staging-backend-1 node dist/db/seeds/scenarios.js --remove
```

Повторный запуск возвращает набор в исходное состояние: даты пересчитываются
от момента запуска, id команд и событий те же (ссылки не меняются), всё, что
главный человек успел нажать в тестовых командах, сбрасывается.

## Защита от прода

1. Без `SEED_SCENARIOS_ALLOW=local` или `SEED_SCENARIOS_ALLOW=staging` скрипт
   не работает. Значения `prod` нет.
2. Отказ без исключений при любом признаке прода: `DB_NAME` содержит `prod`;
   `FRONTEND_URL`, `TELEGRAM_CALLBACK_URL`, `TELEGRAM_WEBHOOK_URL` или
   `PUBLIC_URL` указывают на `pbthub.ru` или любой его поддомен, кроме
   `staging.`; `APP_ENV`, `DEPLOY_ENV`, `ENV_NAME` или `PBTH_ENV` равны
   `prod`/`production`. Окружение проверяется до разбора параметров, так что
   никакой флаг отказ не снимает.
3. Положительные признаки режима: для staging база `*staging*` и адрес
   `staging.pbthub.ru`; для local база на `127.0.0.1`/`localhost`, `NODE_ENV`
   не `production`, адрес приложения локальный.
4. После подключения имя базы перепроверяется по `current_database()`.
5. Перед записью печатается строка `Пишу в базу: <хост>:<порт>/<база>` с
   режимом и адресом приложения.

## Метки и удаление

- Команды: устойчивые id из `ids.ts`, название с меткой « (тест)» в конце,
  короткий код `tst-*`. Метка стоит в конце, а не в начале: знак команды
  берёт первые буквы названия.
- Люди: telegram id `7 700 000 000 001…7 700 000 009 999` (настоящих таких
  нет, сообщение на них не доставляется) и ник `pbth_test_*`.
- Записи журнала: `payload.seedScenarios = "seed-scenarios-v1"`.
- `--remove` удаляет тестовые команды (с ними каскадом события, ответы,
  деньги, заявки, ответы главного человека в тестовых событиях), тестовых
  людей и помеченные записи журнала. Команды, созданные из тестовых заявок в
  консоли владельца, тоже удаляются, если у них есть метка.

## Уведомления

Наполнитель пишет прямо в базу, мимо ручек, которые рассылают сообщения о
новых событиях, слотах и заявках. Авто-напоминания о тестовых событиях заранее
помечены как уже обработанные (служебные строки `event_auto_reminders` с
каналом `ANNOUNCEMENT`; в «Кому дошло» они не видны), поэтому с
`AUTO_REMINDERS_ENABLED=1` приложение не пошлёт напоминание о тестовом событии
ни главному человеку, ни тестовым людям. Это проверяет интеграционный тест.

Что может отправить само приложение, когда главный человек нажимает кнопки в
тестовых командах: «Напомнить», одобрение заявки, открытие слотов, новое или
перенесённое событие. Адресаты — тестовые люди с несуществующими telegram id:
Telegram ответит «chat not found», до людей ничего не дойдёт. Себе главный
человек сообщение может получить, если сам себе напомнит.
