# Event-Centric Expense-First Finance Design

## Goal

Зафиксировать продуктовую и архитектурную иерархию PBTH для событийных финансов:

- `Событие` — первичная сущность приложения.
- `Финансы события` — встроенный вторичный модуль, а не отдельный центр продукта.
- `Траты` — первичный финансовый факт внутри события.
- `Сбор` — производная рабочая область, открываемая на базе агрегированных трат события.

Этот документ корректирует прежний дрейф в сторону `collection-first event screen`, где финансы начинали перехватывать иерархию экрана события.

## Product Invariants

### 1. Event-First Hierarchy

- В PBTH вокруг `событий` строится основной пользовательский сценарий.
- Экран `Событие` не должен превращаться в финансовый рабочий стол.
- Финансовые действия внутри события должны быть доступны, но не должны подменять собой основную сущность события.

### 2. Expense-First Finance

- Сначала капитан фиксирует `фактические расходы`.
- Затем система определяет, `сколько нужно собрать`.
- Только после этого начинается работа со `сбором`.

Иными словами:

`событие -> расходы -> агрегированный итог -> сбор -> начисления/оплаты/корректировки`

### 3. One Event, Many Expenses, One Collection

- Внутри одного события может быть несколько расходов.
- Для события существует один актуальный сбор.
- Сбор строится на основе агрегированных расходов события, а не как параллельная кнопка рядом с расходами.

Сбор не является соседней независимой сущностью. Он дочерний по отношению к расходам события.

### 4. Simplicity First, Depth On Demand

Базовый UX:

- минимальное число действий;
- понятный happy path;
- без перегруза финансовыми абстракциями.

Продвинутый UX:

- при необходимости капитан может провалиться глубже;
- от расхода к сбору;
- от сбора к игроку;
- от игрока к долгу/корректировке;
- из `Казны` в конкретное событие или конкретный сбор.

## Screen Hierarchy

## Event Detail

На карточке `Событие` финансы — вторичный блок.

Что допустимо:

- компактный итог по финансовому состоянию;
- одна основная кнопка: `Добавить расход`.

Что не должно происходить:

- отдельные соседние первичные CTA `Сбор` и `Траты`;
- превращение события в финансовую панель;
- вынесение логики “начать сбор” на тот же уровень важности, что и само событие.

## Event Expenses Workspace

`Добавить расход` должен открывать не просто модалку на одну запись, а рабочую область `Расходы события`.

Внутри неё:

- список всех расходов события;
- редактирование и корректировка расхода;
- общий итог расходов;
- действие `Открыть сбор` / `Открыть сбор по расходам`.

Именно экран расходов является финансовой точкой входа из события.

## Event Collection Workspace

`Сбор` — это отдельная рабочая область, но не главный экран события.

Внутри неё:

- агрегированная сумма к сбору;
- начисления участникам;
- оплата / зачёт перевода;
- напоминания;
- корректировки по игрокам.

## Treasury / Kazna

`Казна` — это сквозной управленческий вход, а не источник истины для событийной логики.

Она должна:

- показывать проблемные сборы;
- показывать очереди подтверждений и должников;
- позволять перейти в конкретное событие / конкретный сбор / конкретного игрока.

Она не должна заменять событийную иерархию.

## Collection Semantics

## Default Model

Рекомендуемая модель по умолчанию:

- у события один живой сбор;
- сбор агрегирует все актуальные расходы события;
- при добавлении новых расходов сбор обновляется;
- если сбор был закрыт и появился новый расход, событие должно перейти в состояние повторного сбора/корректировки, а не оставаться “окончательно закрытым”.

## Why Not “One Expense = One Collection”

Эта модель слишком дробит UX:

- игрок видит много мелких долгов;
- капитану сложнее зачитывать переводы;
- растёт когнитивная нагрузка;
- усложняется back-office логика распределения оплат.

Поэтому `один расход = один сбор` не должен быть базовой моделью.

## Collection Iterations Inside One Event

### Option A — One Live Collection Per Event

Модель:

- у события есть один текущий сбор;
- новые расходы увеличивают целевую сумму этого же сбора;
- закрытый сбор может быть переоткрыт корректировкой.

Плюсы:

- самый понятный пользовательский mental model;
- проще backend state machine;
- проще игроку;
- проще сквозные переходы.

Минусы:

- нужна корректная логика reopen/adjustment;
- требуется чёткое отображение истории изменений суммы.

### Option B — Multiple Collection Iterations Per Event

Модель:

- у события есть несколько раундов сбора;
- например: `первичный сбор`, `досбор после уточнения`, `финальная корректировка`.

Плюсы:

- сильная бухгалтерская трассируемость;
- удобно, если клуб реально живёт раундами “дособора”.

Минусы:

- заметно сложнее UX;
- сложнее объяснить игроку;
- сложнее зачёт перевода;
- выше риск путаницы в открытых долгах.

### Recommendation

Для PBTH базовой моделью должен быть `Option A`:

- один живой сбор на событие;
- дополнительные расходы не создают новый основной сбор, а меняют текущую сумму события;
- при необходимости история показывает, когда и почему сумма изменилась.

`Option B` имеет смысл только если в реальной эксплуатации подтвердится устойчивый сценарий отдельных независимых раундов сбора по одному событию.

## Cross-App Rule

Это правило должно соблюдаться во всех входах:

- Event Detail
- Event Expenses
- Event Collection
- Treasury
- Player debt views
- transfer confirmation / settlement flows

Ни один экран не должен нарушать базовую иерархию:

`event first, expenses first, collection derived from expenses`

## Immediate Design Consequences

- Убрать конкурирующие кнопки `Сбор` и `Траты` на карточке события.
- Перенести точку входа в сбор внутрь `Расходов события`.
- Считать текущий сбор по агрегированным расходам события.
- Внутри сбора дать капитану:
  - авторазнос;
  - доначисление;
  - корректировку долга игрока;
  - напоминания;
  - сквозной переход в карточку игрока и обратно.
- В `Казне` вести пользователя в сущности события, а не подменять их.

## Success Criteria

- Никто в будущих сессиях не трактует `Сбор события` как главный экран события.
- Новые UX-решения не ставят финансы выше события.
- Финансовый workflow начинается с расходов, а не с абстрактного начисления.
- У капитана есть быстрый путь “в три действия”, но при этом остаётся глубокий управляемый слой.
